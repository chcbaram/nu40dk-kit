# 09. 최적화

nRF52840(64MHz Cortex-M4F, RAM 256KB)에서 게임 에뮬레이션, EPAPER 표시, 사운드, BLE 를 함께 돌리기 위해 측정하고 바꾼 것을 정리한다.
측정은 대부분 Super Mario Land(SML) 기준이며, `gb stat` 의 1초 단위 값이다.

## 1. 측정 도구

| 도구 | 내용 |
|---|---|
| `gb bench <frames> [nolcd] [skip]` | 화면 없이 에뮬레이션 속도 (프레임당 시간, 원래 속도 대비 %) |
| `gb stat` | 에뮬 fps/속도, 화면 갱신, 사운드 시간, **스레드별 CPU** (`CONFIG_THREAD_RUNTIME_STATS`), ink 모드 단계별 시간 |
| `epd bench <n> [full\|part\|fast]` | EPD 갱신 속도 (SPI 전송, BUSY 시간) |
| `gb key <keys> [ms]` | CLI 로 게임 입력 (재현 가능한 측정용) |
| `i2s info` | I2S 오류(언더런) 횟수 |
| `epd info` | 갱신 횟수, BUSY 자동 복구 횟수 |

## 2. 에뮬레이터 CPU

| 시도 | 결과 | 채택 |
|---|---|---|
| CGB 지원 빌드 → **GB 전용 빌드** | SML 71% → **108%** (메모리 접근마다 CGB 분기 제거, RAM 32KB 절약) | O |
| **보낼 프레임만 렌더링** (`gbCoreSetDrawNext`) | 렌더링이 프레임 시간의 약 1/3. 60프레임 중 필요한 것만 그려 프레임당 15ms → 7ms | O |
| ROM 읽기 콜백 → 포인터 직접 읽기 매크로 | CPU 를 많이 쓰는 게임(DK) 기준 약 5% | O |
| `-O3` | 71% → 68% (코드가 커져 캐시 효율 저하) | X |
| 핵심 함수 RAM 실행 (`.ramfunc`) | 이득 없음. M4 는 RAM 에서 코드·데이터가 같은 버스. MPU 정렬로 64KB 낭비 | X |
| `long_call` 속성 | 모든 호출이 간접 호출이 되어 107% → 84% | X |
| Peanut-GB / gnuboy | Peanut 은 Walnut 과 동일, gnuboy 는 폴트 | X |

남은 한계: SML 의 무거운 장면은 에뮬 CPU 만 프레임당 14~16ms (예산 16.7ms).

### 2-1. 프로파일링으로 찾은 것 (2026-11-20)

`gb prof [ms]` (TIMER4 인터럽트로 실행 중 PC·LR 샘플링, `addr2line` 으로 집계)와 `gb bench <n> [audio|prof]` (사운드 합성 시간 분리, 명령 캐시 적중률) 를 추가해 측정했다.

| 발견 / 시도 | 결과 | 채택 |
|---|---|---|
| 사운드를 켜면 에뮬이 느려진다? | 같은 입력(bench)으로 비교하면 에뮬 시간은 같음. 사운드 합성은 프레임당 0.4~1.5ms. **에뮬 자체가 100% 에 못 미치는 것이 끊김으로 드러난 것** | - |
| `__gb_draw_line` 첫 줄 `uint8_t pixels[160] = {0}` | 프레임 스킵으로 그리지 않는 줄에서도 매번 memset → **실제 플레이 실행 시간의 13~17%**. 스킵 판단 뒤로 옮기고 32비트 배열로 | **O** |
| 툴체인 picolibc 의 memset/memcpy | 크기 최적화 빌드라 **1바이트 루프**. `CONFIG_PICOLIBC_USE_MODULE=y` 로 소스에서 속도 최적화 빌드 (FLASH +5KB) | **O** |
| Walnut·minigb_apu 만 `-O3` | +1.5% | O |
| ROM 앞 32KB 를 RAM 에 복사 | 변화 없음 (플래시 캐시가 이미 처리) | X |
| 메모리 읽기 4KB 페이지 포인터 표 (인라인) | 코드 +11KB, 5% 느려짐 | X |
| `-Os`, LTO | 더 느림 | X |
| 명령 캐시 | 미스율 4.8~7% | - |

| 측정 | 전 | 후 |
|---|---|---|
| `gb bench 1200` (매 프레임 그림) | 19.9ms (84%) | **17.3ms (96%)** |
| 실제 1-1 플레이, 사운드 켬 | 61~71% | **85~88%** |

| `lcdLineCb` 32비트 묶기 | 4픽셀을 한 번에 읽고 `((v & 0x03030303) * 0x40100401) >> 24` 로 2비트 4개를 한 바이트에 | O |

## 5. EPAPER 전송과 갱신

| 시도 | 결과 | 채택 |
|---|---|---|
| SPI 8 → 16MHz | 15KB 전송 15.5ms → 7.9ms. 32MHz 는 비트 오류(무작위 점). **Phase 8 에서 게임 중 데이터 손실이 확인되어 8MHz 로 되돌림** | X |
| 게임 영역 320px 줄 단위 전송 (576번) | 디스플레이 CPU 22~24% | X |
| 전체 폭 400px 14KB 한 번 DMA | CPU 1% 지만 화면 아래쪽 누락·멈춤 | X |
| **전체 폭 4KB 씩 분할 DMA** | CPU 2%, 정상 | O |
| EPD 는 SPIM2 8MHz (Phase 8) | 16MHz 이상은 SPIM3 만 가능. SPIM3 를 쓰려면 TX 버퍼를 CPU 가 안 쓰는 전용 RAM 블록(0x20000000~0x2000FFFF 8KB 블록)에 두고 나눠 보내야 하며, 16MHz 는 SSD1683 홀드 시간도 위반 | 보류 |
| 부스터 소프트 스타트 90 → 30ms, 아날로그 유지(0x8C) | 갱신 고정 오버헤드 110ms → 9ms | O |
| 커스텀 LUT FAST + **hold 구동** | 잔상은 적지만 정지 화면에도 같은 방향 전압이 계속 걸려 **DC 누적 → 패널 잔상** | X (Phase 7) |
| EOPT 0x07, ±17V | 점 발생 | X |

## 6. ink 모드: 픽셀(블록)별 펄스 카운터 (Phase 8)

InkBoy(https://github.com/kuslota/InkBoy, MIT)의 방식을 nRF52840 메모리에 맞게 옮긴 것이다.

| 항목 | InkBoy | 11_game |
|---|---|---|
| 카운터 단위 | 패널 픽셀 (200×200) | **GB 픽셀 = 화면 2×2 블록** (160×144). 2배 확대라 블록 안 4픽셀이 같이 바뀜 |
| 카운터 | 4bit × 비트 슬라이스 | 4bit × 비트 슬라이스, **11.5KB** |
| 변하지 않은 픽셀 | HOLD (전압 0) | 같음 |
| 바뀐 픽셀 | 예산만큼 구동 후 HOLD | 같음 (예산 8, 스캔당 3프레임 = 24ms, 총 192ms) |
| EPD RAM | 두 면을 검정/흰색 마스크로 | 같음: RED = 검정 마스크, BW = 흰색 마스크 (커스텀 LUT hold 0 이 그대로 지원) |
| 마스크 버퍼 | 5KB × 2 | 14.4KB (검정) + 캔버스 버퍼 재사용 (흰색) |

### 메모리

| 항목 | 크기 |
|---|---|
| 카운터 (4 × 720 워드) | 11.5KB |
| 회색 모드 방향 비트 | 2.9KB |
| 현재 목표 (2bpp 160×144) | 5.8KB |
| 검정 마스크 (전체 폭 288줄) | 14.4KB |
| 흰색 마스크 | 0 (캔버스 15KB 재사용. 게임 메뉴를 그리기 전에 이미지 복원) |
| **합계** | **약 35KB** (RAM 246KB / 256KB) |

패널 픽셀 단위 카운터(InkBoy 와 완전히 같은 방식)는 약 58KB 가 필요하다. 스택(약 12KB), 믹서(8KB), cart RAM 공유로 확보할 수 있으나 블록 단위로도 효과가 같아 보류.

### 화질 실험 (ink 모드)

| 실험 | 설정 | 결과 | 채택 |
|---|---|---|---|
| 제조사 전압/VCOM | Waveshare EPD_4in2_V2 4Gray LUT 의 VGH 0x17, VSH1 0x41, VSH2 0xA8, VSL 0x32, VCOM 0x30 | 체감 차이 없음. 켠 상태에서 **패널이 구동되지 않는 멈춤**(전체 갱신 114ms, BUSY 복구)이 생겨 `epd init` 으로 회복 | X (`epd opt <fr> 1` 로만) |
| 50Hz 1프레임 (제조사 FR 0x02) | InkBoy 와 같은 스캔당 약 20ms | 체감 차이 없음. 방전(EOPT 2프레임)도 50Hz 라 스캔 56 → 76ms | X |
| 카운터 3bit → **4bit**, 예산 8 | InkBoy 기본값 | 유지 (RAM +2.9KB) | O |
| **회색(grayscale) 모드** | 디더 대신 2×2 블록을 한 방향으로 전환별 펄스 수만큼 구동 (InkBoy 표 + 검정 쪽 증가) | 디더 점이 사라져 부드럽지만 **검정이 옅고 잔상이 많음**. 펄스 수 열린 제어라 오차 누적, 패널 기존 잔상의 영향도 큼 | X (`gb gray on` 실험 옵션) |

| **바뀐 디더 점만 구동** (`ink_base`) | 블록 단위 카운터는 블록 안 4점을 모두 구동해 이미 목표색인 점이 같은 방향으로 과구동됐다 (지나간 자국, 작은 DC 누적). 바뀌기 직전 목표를 저장해 패턴이 다른 점만 구동 | 잔상 조금 줄어듦. RAM +5.8KB (252KB), 마스크 생성 스캔당 5~6ms 로 늘어 스크롤 중 에뮬 61~75% (사운드 끄면 85~96%) | O |

| **회색 모드 펄스 균형** | 검정 방향만 늘리면(흰→검 12, 검→흰 7) 검었던 자리가 회색 잔상으로 남음. 흰색 방향도 같은 비율로 | 잔상 줄어듦 | O |
| **회색 모드 32ms 펄스 × 절반 횟수** | 스캔당 고정 비용(SPI + 방전 약 30ms)이 커서, 펄스를 16 → 32ms 로 늘리고 횟수를 절반으로 하면 한 번 바뀌는 시간이 약 0.6 → 0.38초 | **움직임 잔상 줄어듦**. 회색 모드를 기본값으로 | O |
| **EPD SPI 16 → 8MHz** | 게임 중 화면 아래쪽 일부가 갱신 안 됨. 8MHz 에서 일단 정상 | 스캔당 SPI 15 → 29ms | O |
| **마스크 증분 생성** | 마스크를 매 스캔 지우고 다시 만들지 않고, 명암이 바뀐 묶음과 카운터가 0 이 된 묶음(마스크 4바이트)만 다시 계산 | 디스플레이 CPU 11~15% → **4~6%** | O |
| 바뀐 줄만 전송 | 마스크가 바뀐 줄 범위만 EPD 로 전송 | **화면이 깨짐**. SSD168x 는 구동 후 RAM 을 BW↔RED 로 복사하는 것으로 보여 EPD RAM 이 이전 마스크를 유지하지 않는다 (InkBoy 도 매 스캔 두 면 전체 전송) | X |
| **프레임 가져오기를 스캔과 분리** | 디스플레이가 스캔 끝에 프레임을 요청하면 2 스캔에 1 프레임(초당 4개, 약 15프레임 스킵) → 마리오 다리가 움직이지 않음. 에뮬레이터가 83ms 마다 스스로 그려 두고 스캔 시작 때 최신 프레임을 가져감 | 초당 4 → **10~13 프레임**, 다리 움직임 보임. 에뮬 속도 약간 하락 | O |
| **EPD SPIM3 → SPIM2** | 프레임을 자주 그리자 8MHz 에서도 아래쪽 누락 재발. 원인은 **nRF52840 errata 198**: SPIM3 TX 버퍼가 CPU 와 같은 RAM 블록(0x20010000 이상 RAM8 은 한 블록)에 있으면 전송 데이터 손상. nrfx 우회(0x40000E00)로는 부족. 8MHz 만 쓰므로 errata 없는 SPIM2 로 옮김 (핀 동일) | **정상** | O |

InkBoy 와의 화질 차이는 패널 해상도(184ppi, GB 1픽셀 = 패널 1픽셀 vs 120ppi, GB 1픽셀 = 2×2), 초당 30회 갱신, 카메라 측정 튜닝, 패널 상태 차이로 본다.

### `gb bench` 160% 와 실제 플레이 속도의 차이

`gb bench 600 skip` 은 전원 직후 600프레임(닌텐도 로고·타이틀·데모, 대부분 HALT)을 에뮬레이터만 단독으로, 렌더링 절반으로 돌린 최대치다.
실제 1-1 플레이는 장면이 무겁고, 사운드(프레임당 1~1.5ms)와 디스플레이 스레드(CPU 8~13%), BT·I2S 가 함께 돈다.
실제 장면 성능은 게임을 `gb key` 로 진행시킨 뒤 `gb stat` 으로 잰다.

## 9. 보드 변경 검토: NU87-TinyDK (RTL8720DF) — 보류 (2026-11-20)

| 항목 | NU40DK (nRF52840) | NU87 (RTL8720DF) |
|---|---|---|
| CPU | M4F 64MHz 싱글 | **M33 200MHz** (+ M23 20MHz) |
| RAM | 256KB (96% 사용) | 앱 456KB (+ BT 미사용 시 64KB) |
| Flash | 1MB | 4MB (DSPI XIP) |
| SPI | SPIM2 8MHz (SPIM3 errata 198) | SPI0 50MHz, SPI1 25MHz |
| I2S | MAX98357 | 있음 (PB19 SD_TX0, PB20 CLK, PB21 WS). QFN48 은 내장 아날로그 출력 없음 → 외부 앰프 |
| 무선 | BLE (Zephyr) | BLE 5.0 + WiFi (Realtek 스택) |

- 기대 효과: 에뮬 CPU 약 1/3, SPI 20MHz(SSD1683 최대)로 두 면 전송 약 9ms → 스캔 초당 20~28회 + 에뮬 100% 유지, RAM 여유로 픽셀 단위 카운터·도달 수준 추정 가능.
- 걸리는 점: I2S 와 SPI0 핀 공유 → EPD 는 SPI1(PA12/14/15, RGB LED 버퍼 입력과 공유). 제어선은 PB1/PB2/PB18 등. 보드에 SD·버튼 4개·앰프 없음. Realtek SDK(FreeRTOS) 로 이식, **Xbox BLE 패드(central + HID GATT 클라이언트)를 Realtek 스택으로 새로 구현**해야 함.
- 근거: `NU87-TinyDK/firmware/docs/01-hardware.md`, `hardware/ameba_datasheet_rtl872xd_v4.8.pdf` (SPI0 50MHz / SPI1 25MHz, I2S 샘플레이트 표).
